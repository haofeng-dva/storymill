# 并行调度设计：多章节并发写作

- 文档版本：v1.1（2026-08-19，块状并行 v1.1 落地）
- 对应代码：engine.py 写章循环 / orchestrator.py 调度层
- 状态：路线三（块状并行）已实施，待跑 M1 小实验验证后选优

---

## 1. 背景与问题

当前 `engine.py` 的分章写作是**串行**的：ch1 写完才写 ch2，12 章逐章排队。每章耗时约 2-4 分钟（分段写 + 盲评 + 可能重写），一部 12 章短篇总耗时 30-40 分钟。

**瓶颈不是模型慢，是排队慢**：ch1 在写的时候，ch2 到 ch12 全部空等。目标是在不牺牲章节连贯性的前提下，把写章阶段耗时压缩到串行的 1/3 到 1/4。

> 注意：以下提速数字均为**预估**，需落地后用实际运行数据验证，不得写入对外报告作为实测结论。

## 2. 依赖链分析（设计前提）

### 2.1 现状：每章的输入是什么

从 engine.py 的 prompt 构造看，写第 n 章时模型拿到的上下文是：

| 输入 | 说明 | 并行是否会丢 |
|---|---|---|
| direction（方向）| 全局，不依赖章节 | 不会 |
| outline beats（大纲节拍）| 全局，写章前已生成 | 不会 |
| world_bible（设定圣经）| 全局，写章前已生成 | 不会 |
| lessons（本书教训词条）| 依赖前章盲评结果 | 部分会 |
| 前章正文 | **现状就没有传入**（串行也不传）| 不适用 |

关键事实：**串行时下一章也拿不到前一章的全文**。章节连贯性靠的是 outline 的节拍约束 + world_bible 的 MUST stay consistent，而不是前文回传。因此"并行会导致上下文缺失"的担心不成立——上下文锚点（大纲/圣经）是全局共享的。

### 2.2 真实风险点

并行真正会松动的是**章节接缝**（章与章之间的衔接处）：

1. **钩子对不上**：ch1 结尾停在哪个场景、哪个人物状态，ch2 开头不知道，可能出现"ch1 结尾在车库，ch2 开头在卧室"
2. **风格轻微漂移**：12 个 writer 并行开工，每章生成随机性让"声音"轻微跑偏（串行也有此风险，并行会放大）

### 2.3 依赖链结论

章节之间存在**链式顺序依赖**（写第 n 章最好知道第 n-1 章如何收尾），但依赖的是"收尾状态"而非"全文"。因此依赖链不能靠并发绕过，只能二选一：

- **预生成**：在写作开始前，把每章结尾状态钉死（预承诺）
- **后修复**：写完后统一修补接缝

## 3. 方案评审记录（重要）

### 3.1 已否决方案：滑动窗口 + 写后交接卡

初版设想：窗口内 3 章并行，谁写完谁补位，写完即生成"交接卡"（本章结束时人物位置/情绪/钩子）喂给后续章。

**缺陷（评审发现，设计不成立）**：

> 123 并行 → 2 先写完交卡 → 4 入队开写 → 但 4 只拿到 2 的卡，没拿到 1 和 3 的卡（1、3 未写完）→ 4 与 3 同时承接 2 的结尾 → 内容撞车 / 重复。

结论：**交接卡在"写完后"生成，时机太晚**。滑动窗口只能保证并发数量，保证不了依赖链完整。此方案废弃，禁止按此实施。

### 3.2 设计原则（本次定稿）

1. 交接信息必须**在写作开始前预生成**（预承诺），或在全部写完后统一修复（后修复）
2. 并发度必须可调（受 API 限流约束，默认保守）
3. 串行模式保留为回退选项，`--serial` 开关
4. 块内依赖链必须完整传递，块间接缝单独处理

## 4. 实施方案

### 4.1 路线三：块状并行（v1.1 落地，推荐起步）

把 12 章切成 N 块（默认 4 块 × 3 章），**块内串行 + 块间并行**。

```
块1: ch1 → ch2 → ch3   （串行，交接卡完整传递）
块2: ch4 → ch5 → ch6   （串行，交接卡完整传递）
块3: ch7 → ch8 → ch9   （串行，交接卡完整传递）
块4: ch10 → ch11 → ch12（串行，交接卡完整传递）
        ↑ 四块同时开跑（ThreadPoolExecutor，max_workers = 块数）
```

- 块内串行：每章写完生成交接卡（人物位置/情绪/钩子/时间线），注入下一章 prompt，**块内依赖链 100% 完整**
- 块间接缝：块与块之间只留 N-1 个接缝（4 块 = 3 个接缝），写完统一走一次"接缝修复"（见 4.3）
- 提速：约等于块数（4 块 ≈ 3-4 倍，受限流影响），预估写章阶段从 30-40 分钟压到 10-15 分钟

### 4.2 路线一：预承诺（v1.2 进阶，并行度拉满）

在 outline 阶段追加"每章结尾预告"：大纲 agent 为每一章预先写明本章结束时的状态（人物位置、关键信息、钩子）。预告不依赖正文，一次调用全量生成。

- 12 章全并行，每章 prompt 注入"上一章结尾预告 + 本章结尾预告"
- 写完后做"实际结尾 vs 预告"一致性检查，偏差处定点修
- 提速上限最高（接近满并行），但对 outline agent 的预告质量要求高
- **前置条件**：v1.1 验证通过后实施，且先做 3 章小实验对比串行/块状/预承诺三者的衔接质量与耗时

### 4.3 接缝修复流程（两种路线共用）

块间接缝（或预承诺偏差处）由"主编 agent"统一修复：

1. 输入：相邻两章的实际结尾 + 实际开头
2. 任务：只改开头第一段或结尾最后一段，把钩子接上，**禁止重写正文**
3. 修复后跑一次 continuity 盲评（见 5），不达标重修，最多 2 次

接缝数量有限（N-1 个），修复成本远低于正文写作，不会成为瓶颈。

## 5. 质量保障

### 5.1 盲评新增维度：continuity（衔接度）

现有盲评只有 naturalness（自然度），并行后新增 continuity 维度：

| 维度 | 检查内容 | 门槛 |
|---|---|---|
| naturalness | 是否像真人写作（已有）| ≥4 |
| continuity | 本章开头是否接住上一章结尾 | ≥4（新增）|

不达标触发带反馈重写，机制与现有质量门槛一致。

### 5.2 lessons 回灌在并行下的行为

- 块内串行时：lessons 词条照常从本章沉淀、注入块内下一章，行为与现状一致
- 块与块之间：词条以"上一块已沉淀"状态传给下一块起始章
- 首轮并行时 lessons 会略滞后于串行（前块的教训来不及影响同批后块），这是并行化的已知代价，记录在案，不视为缺陷

## 7. 风险与回退

| 风险 | 应对 |
|---|---|
| API 限流（并发撞墙）| max_workers 默认 = 块数且保守（先 2-3），config 可调 |
| 块间接缝质量不稳 | continuity 盲评兜底 + 主编修复最多 2 次 |
| 并行后耗时反而更久（限流重试）| `--serial` 一键回退，对比耗时后决定 |
| 提速数字夸大 | 落地后实测记录，报告只写实测值 |
